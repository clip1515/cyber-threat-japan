# Phase 2-E 段階0 暫定運用手順(NVD取得上限・H3)

| 項目 | 内容 |
|---|---|
| 対象 | 段階0(PR #14)を本番導入した後の日次運用 |
| 状態 | 採用済みの暫定ルール。本番導入は別途承認する。本書は導入を承認するものではない |
| 見直し | NVD 部分: 取りこぼしの回収方法(§1.5)を決めたとき<br>H3 部分: 通知台帳を実装したとき(実装した時点で §2 は廃止する) |

本書の手順は**確認と記録だけ**で行う。手順の中で、ワークフローの再実行、コード・設定・Secrets の変更、本番DBの操作が必要になった場合は、その都度、個別の承認を得る。
記録(§3)には実行時の情報が入るため、公開リポジトリには置かず、運用者の手元で管理する。

## 0. 前提(実装に基づく事実)
| 項目 | 内容 |
|---|---|
| 定時実行 | 毎日 22:17 UTC(07:17 JST)。GitHub 側の遅延で遅れることや、実行されない日があり得る |
| 公開されるもの | `data/threat_intel.db`、`daily_report.md`、`docs/data/dashboard_data.json`、`reports/daily_report_<日付>_run<N>.md` だけ。公開すると main に `chore: daily update <日付>` のcommitが作られる |
| 通知の条件 | 公開が成功した場合だけ送る。ntfy とメールは互いに独立して送る |
| ntfy の結果 | `sent` / `failed_definite`(届いていない)/ `unknown`(届いたか不明) |
| 失敗アラート | ジョブが失敗すると ntfy に `cyber-threat-japan FAILURE` が届く。本文に `daily ntfy summary: <結果>` が入る。ntfy 自体が止まっていると、このアラートも届かない |
| 自動再送 | **行わない**。ntfy の既定のリトライ回数は0。暫定運用の間は再送の仕組みを使わない |

## 1. NVD 取得上限(1回あたり最大2,000件)

### 1.1 仕様
- 取得対象: 過去8日間に更新された(`lastModified`)CVE。1回の取得上限は2,000件(`MAX_PAGES = 1`)。
- 上限を超えた分は**未取得**となる。未取得分が次回以降の実行で回収される**保証はない**。理由は2つある。
  - NVD がどの順で結果を返すかは未確認。
  - 再び更新されなかったCVEは、8日を過ぎると取得対象の期間から外れる。
- 収集時に NVD の API キーは使っていない。未認証のレート制限で、1回あたり1リクエストを送る。

### 1.2 日次の判定(§2.2 の毎朝の確認の中で行う)
| 通知・ログの内容 | 判定 |
|---|---|
| NVD に関する警告がない | 全件取得 |
| `全件を取得できなかったソース: NVD CVE API 2.0(取得上限(1ページ・2000件)に達したため<総件数>件中2000件のみ取得。残りは未取得)` | 部分収集 |
| `取得に失敗したソース: NVD CVE API 2.0` | 取得失敗(取得件数0) |
| `収集品質を確認できません` | 品質不明(Actions のログで NVD の行を確認する) |

通知が届かなかった日は、同じ内容を次の場所で確認する。
- Actions のログ行 `collector nvd_cve: 取得上限…`
- 公開レポートの冒頭(収集結果の行)

### 1.3 記録(部分収集が発生した当日から行う)
部分収集・取得失敗・品質不明の日は、NVD 監視記録(§3.1)に次を記録する。
- **総件数:** 通知またはログの「<総件数>件中」
- **取得件数:** 部分収集なら 2,000。取得失敗なら 0
- **未取得件数:** 総件数 − 取得件数。取得失敗で総件数が分からない日は「不明」とする

その日は、NVD に基づく「CVE・CVSS の変化なし」を**未確認**として扱う。
悪用されているCVEは、毎回全件を取得している KEV の結果で確認する。KEV 自体の取得失敗が出ていないことも確かめる。

### 1.4 回収方法を再検討する基準
次のどれか1つに当てはまったら、回収方法の再検討を依頼する。
- 部分収集が**3日連続**した
- 1日の総件数が**4,000件以上**になった
- **7日間のうち4日以上**が部分収集だった

### 1.5 回収方法の候補(決定と実施には、それぞれ承認が必要)
| 方法 | 内容 |
|---|---|
| a | 取得期間(現在8日)を短くし、1日分が2,000件に収まるようにする。1日の取りこぼしに備えた重なりは残す(コード変更) |
| b | DBの増加量に予算を決めたうえで、上限を上げる。DBは毎日commitされ、GitHubには1ファイル100MBの上限がある(コード変更) |
| c | 取りこぼした期間を、承認済みの単発実行で回収する(上限を一時的に上げたうえでの workflow_dispatch) |
| d | NVD の部分取得を受け入れ、悪用されているCVEは KEV で把握する(運用ルールの変更) |

## 2. H3(通知されなかった変化の持ち越し)

### 2.1 リスク
公開は成功したが通知が届かなかった回の変化は、**翌日以降の通知には出ない**。対象は、新規KEV・Critical/High・重要度の上昇・日本組織への実被害。
データはDB・ダッシュボード・その回の公開レポートには残る。

### 2.2 毎朝の確認(09:00 JST、通知の有無にかかわらず毎日行う)
1. **Actions:** 当日の `Daily Cyber Threat Japan Update` の実行を確認する。
   - 実行の有無を見る。実行されていなければ、それ自体を記録対象とする。
   - 実行されていれば、結果(成功/失敗)と、失敗したステップを見る。
2. **公開:** main に当日の `chore: daily update <日付>` のcommitがあるかを確認し、あれば run_id を控える。
3. **公開レポート:** `reports/daily_report_<日付>_run<N>.md` を開き、次を確認する。
   - 冒頭の行(「重要な変化を検出しました」か「重要な新規変化はありません」か)
   - `本日の新規脅威`、`Critical / High`、`日本企業・日本組織への実被害`、`悪用確認済みCVE (CISA KEV等)`
4. **通知:** ntfy・メールの日次通知が届いたかを確認する。Actions の ntfy ステップのログから、結果(`sent` / `failed_definite` / `unknown`)を控える。
5. **NVD:** §1.2 の判定と §1.3 の記録を行う。

### 2.3 通知が届かなかったrunの扱い
- 09:00 JST の時点で、その日の日次通知(いずれのチャネルでも)が届いていない run は、すべて H3 手動台帳(§3.2)に記録する。
- 公開commitの有無で、扱いを次のように分ける。
  - **公開commitがある(公開成功・通知未着):** §2.2 の3で確認したレポートの内容を台帳に記録する。重要な変化があれば、関係者へ手動で共有する。
    - ntfy の結果が `unknown` なら、受信できていたかも確認し、確認結果を台帳に記録する。
  - **公開commitがない:** 公開が行われなかったため、通知ステップは実行されない設計になっている。ただし、**それだけで通知処理が正常だったとは判断しない**。次を確認して台帳に記録する。
    - run が存在したか(定時実行が起動しなかった可能性)
    - どのステップで止まったか
    - 失敗アラートが届いたか(届かない場合は、ntfy 自体の障害も疑う)
    - 次回の run で、同じ変化が新規として検出されたか(公開されていないDBから再収集されるため、再検出される見込みはあるが、保証はない)

### 2.4 してはいけないこと
- 通知を出し直すための自動再送や、ワークフローの手動再実行。新しい run が作られ、前回の変化は差分に含まれない。
- 公開済みのDBやレポートの編集。
- Secrets の変更。

### 2.5 将来の通知台帳との関係
通知台帳(チャネル別の状態管理と再送)の設計は別ブランチで検討中で、main には未導入である。
導入されるまでは、本書の手動台帳と「自動再送なし」を正とする。

## 3. 記録の形式(運用者の手元で管理する。公開リポジトリには置かない)

### 3.1 NVD 監視記録
`日付(JST) | run_id | 判定(全件/部分/失敗/品質不明) | 総件数 | 取得件数 | 未取得件数 | 再検討基準への該当(なし/3日連続/4,000件以上/7日中4日) | 確認者 | 補足`

### 3.2 H3 手動台帳
`日付(JST) | run_id(または「runなし」) | 公開commit | 止まったステップ | ntfy結果 | メール結果 | 失敗アラート受信 | 重要な変化(有/無/未確認) | 確認したレポート | 共有先・日時 | 確認者`

### 3.3 週次の確認
- 台帳に、確認や共有が終わっていない行がないことを確かめる。
- 失敗アラートが届かなかった週でも、Actions の実行一覧で失敗と未実行がないことを確認する。
- NVD の再検討基準(§1.4)に該当していないかを確認する。
